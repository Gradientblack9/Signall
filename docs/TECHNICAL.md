# Signal Stack technical guide

## 1. Architecture and boundaries

The application serves a buildless HTML/CSS/JavaScript dashboard from FastAPI. Eight hash-routed pages call JSON API endpoints. Synchronous work runs in FastAPI's thread pool; longer company operations run in a bounded two-thread job executor. SQLite stores source-of-truth records. APScheduler 3 supplies four per-company schedules: weekly pipeline, monthly audit, interval crawl, interval discovery refresh. Run a single server process/worker.

The architecture is `dashboard → FastAPI → Engine → Fetcher + LLM → SQLite`. `app/main.py` owns request validation, access checks and routes. `services.py` owns research through briefing. `network.py` controls HTTP retrieval and free search. `llm.py` validates responses against Pydantic models, retries three times and caches for seven days. `jobs.py` serializes long operations per company and records their outcomes. `briefs.py` defines the assignment report and `filtering.py` implements feed filters; `exports.py` generates three export formats.

No paid scraping service or search API is used. Public search runs under robots policy. If it is blocked, Gemini proposes 24-36 URL hypotheses. Each new candidate must be successfully retrieved under the same public-URL and robots checks before its actual text is scored. Guessed, blocked and empty URLs are rejected and logged. This fallback uses no preconfigured business sources. Country aliases do not inflate competitor counts. Candidate scores are estimates, not verification of claims.

## 2. Data model and context

Required tables are companies, profile_answers, sources, crawl_runs, documents, signals, briefs, actions, job_logs and settings. Additional tables hold llm_cache and context_changes. Foreign keys are enforced per connection. SQLite uses WAL and a 30-second busy timeout. Values use bound SQL parameters; dynamic SQL identifiers are application constants.

Company profiles contain summary, industry, customers, products, priorities, facts and competitor candidates. Interview answers retain their question and position. They are part of structured strategic context. Ten positions are enforced by the service and a unique company/position constraint. An unanswered question resumes instead of generating another one.

Editing the profile increments context_version, records a unified diff, marks sources stale, and queues reassessment. Editing an interview answer also versions context and records a before/after change. Reassess after completing the interview to avoid repeatedly consuming quota while answering. Reassessment updates source relevance/reasons, flags low-relevance sources and regenerates signals under the current context. Reassessment also attempts discovery of new candidates and records its limitations. Unmatched source IDs are discarded. Old briefs remain immutable snapshots. Current briefs omit stale-context signals.

Documents store original URL, text, title, content hash, publication date if known, discovery date and previous document ID for changed content. Sources can be deleted without losing their historical documents; the foreign key becomes null. Internal upload URLs resolve to saved extracted text in the authenticated app. Original binary uploads are not retained. Re-uploading identical text does not duplicate evidence.

## 3. Evidence, interpretation and ranking

Untrusted web/upload text is explicitly identified as data in LLM prompts. Pydantic validates outputs; unsupported JSON or invalid enums/scores trigger retry rather than loose parsing. Accepted source URLs must match actual search results or successfully retrieved candidate pages. Profile fact excerpts must match retrieved page text, otherwise they become assumptions. Signal evidence excerpts must match collected document text, otherwise the signal is rejected. Whitespace and case are normalized for the check; the model cannot provide a new source URL for a signal.

A matched excerpt is labeled source-reported, with verified=false. Independent verification requires an explicit review note through the verification API. Quote matching and AI evidence strength never prove that the event is true. Profile fact labels mean source-matched claims; the original assertion still needs corroboration. Source snippets and quoted assertions are kept separate from AI-authored importance, sentiment, urgency and suggested actions. Unknown publication dates remain null; discovery dates are never relabeled publication dates.

Ranking is deterministic given the LLM assessments: relevance 25%, impact 20%, urgency 15%, credibility 15%, recency 15%, novelty 10%. Relevance, impact, urgency and evidence strength are LLM estimates between 0 and 1. Credibility averages source credibility and evidence strength. Source reliability is separately updated after crawl success/failure and stored on every signal. Strategic relevance is separately stored. Recency decays as `exp(-age_days/14)`; unknown publication dates score 0.35, and implausible future dates score zero. Novelty is 1 for a new URL and 0.5 for changed evidence at a known URL. Every signal stores the factors, weights and explanation.

The assignment's ten sections are Executive Summary, Customer Signals, Competitor Intelligence, Market Intelligence, Internal Business Intelligence, Opportunities Identified, Risks & Threats, Recommended Actions for This Week, What We Should Watch, and Source Appendix. Opportunities include evidence, impact, next step and priority; actions suggest a role. The appendix preserves dates and verification status. Background pages and explicitly old articles do not become current headlines. Unknown dates stay unknown. A separate grounded opportunity pass may propose responses to existing risks, clearly labeled as recommendations rather than new events. Every supporting signal ID must exist in the current context. Unsupported opportunity counts remain visible shortfalls.

## 4. Reliability, compliance and security

Every public URL and redirect is checked for http(s), standard ports, credentials and public resolved addresses. Loopback, RFC1918, link-local and reserved destinations are blocked by the crawler. DNS rebinding is not fully pinned at the transport layer; public hosting must also restrict outbound private-network traffic. HTTP responses are limited to 3 MB, with finite timeouts and a six-hop redirect bound. The configured Ollama endpoint is server-owned configuration and can use loopback.

Robots policies are checked for every origin, cached for one hour and honored across redirects; canonical-host robots redirects are safely validated too. A missing robots file (404) allows crawling; other retrieval/policy errors defer it. Request spacing is at least one second, or the site's declared crawl delay. Declared delays over 60 seconds are deferred. Authentication restrictions are logged; the app never circumvents logins/paywalls or executes fetched JavaScript. Dynamic sites with little readable HTML are marked accordingly. RSS is preferred. If a feed is blocked, permitted HTML remains usable; a bounded same-site sample of up to three article links supplies HTML fallback records. Every article is checked separately.

Each crawl source is isolated and records a crawl_runs outcome. All-source failure fails the job; partial failures produce a partial job result. LLM responses retry with exponential spacing and default to at least four seconds between live request starts. API keys are server-side environment variables; provider request URLs and keys are not written to job logs. Cache keys are hashes of provider/model/task/context, so changing context prevents accidental response reuse. Cache entries are retained on disk; delete database rows to remove historical cached content.

The app is single-user. Optional bearer authentication protects API routes; there are no per-user roles or tenant authentication. Company scoping is enforced by route queries. Cross-origin writes are rejected; no permissive CORS middleware is installed. CSP blocks third-party script execution and framing. The default server and Compose ports bind loopback. Use TLS, an access token and outbound network restrictions for remote exposure. Generated HTML escapes all data. Internal record links need authenticated API requests when the token is enabled; open them from the signed-in dashboard evidence viewer.

Uploads are capped at 10 MB, 1,000 records, 100 PDF pages and 40 MB uncompressed XLSX content. Scanned PDFs require OCR outside this app. Analysis processes up to 100 eligible documents per run; discovery uses up to six queries/eight results each, or at most 36 verified URL hypotheses. Feed filters cover competitor, dates, relevance, impact and verification, with chronological or importance ordering. These caps are visible operational limits rather than promises of exhaustive research. Uploading internal notes sends their extracted text to the selected LLM when analysis runs; only use records appropriate for that provider's data terms.

## 5. Operations and validation

Use Python 3.11+ (3.13 tested), install requirements in a virtual environment, copy .env.example and add a free-tier Gemini key. Run one Uvicorn worker. `/health` checks SQLite and reports LLM configuration presence; **Test connection** performs an actual provider call. `/docs` exposes the API schema. Settings are persisted per company. Timezone names are IANA identifiers; tzdata supplies Windows support.

APScheduler schedules are reconstructed from persisted settings on startup. Job records left queued/running after a process restart are marked failed. Per-company job collisions are logged as skipped and can be retried. A weekly run calls crawl, analyze and brief in order. Monthly audits check dead/blocked URLs, duplicate domains, inactive sources and low/stale relevance, re-score the stack, and try discovery. No source is silently rejected by an audit. In-process schedules do not catch up work missed while the machine was off; use an always-running host for reliable cadence. Tests fire the registered weekly job through APScheduler with a short test trigger; production Monday delivery still requires an online host.

Back up SQLite using `sqlite3.Connection.backup()` while running, or stop the server before copying the database. Do not copy only the database file from a running WAL database. Treat all data, caches, logs and internal evidence as private. Docker runs an unprivileged user, mounts a persistent data folder and uses a single worker. The Docker image configuration has not been executed unless recorded in acceptance evidence.

Tests inject explicit synthetic web and LLM implementations into Engine and create isolated temporary databases. They check different company questions/stacks/briefs; candidate approval; quote grounding and hallucination rejection; hash deduplication and versioning; all supported upload parsers; weighted ranking; PDF/HTML/Markdown export; context-change diffs; source isolation; auth and settings; job outcomes and scheduler callbacks. Live acceptance must additionally demonstrate actual web collection and provider output with three companies. Missing credentials never turn into fabricated signals. See ACCEPTANCE.md and PHASES.md for current release gates.
